# 美国大学生数学建模竞赛校赛模拟赛：三人团队协作与任务分工方案

## 一、总体协作思路

我们采用「三人独立分析 → 交换意见 → 共同确定方案 → 分工执行 → 独立检查 → 统一整合」的协作模式。

每位成员都有自己的 Codex 和 Mathodology 智能体。三个智能体既可以独立思考，也可以通过共享文件和讨论结果相互交流。

我们的目标不是让三个人分别完成三份完整的建模论文，而是充分利用三个智能体的独立分析能力，尽可能发现不同的解题思路和潜在问题，最终形成一套统一、合理、能够验证的解决方案。

**基本原则：**
- 重要决策先独立思考，再集中讨论，避免一开始就相互影响。
- 每个人都需要理解整体建模思路，不能只负责自己的一小部分。
- 每项工作明确一名主要负责人，其他成员负责协助或检查。
- 所有重要结论、数据和实验结果都要有记录，不能只保留在聊天记录中。
- AI 提供建议和分析，最终决策由团队成员共同完成。

---

## 二、三名成员的主要职责

| 成员 | 主要定位 | 核心职责 |
|---|---|---|
| A | 建模与代码负责人 | 负责核心模型设计、数学推导、代码整合与主要论文撰写 |
| B | 算法与实验负责人 | 负责替代方案、算法实现协助、实验测试和图表制作 |
| C | 独立验证与论文负责人 | 负责模型检查、结果验证、论文审查和最终整合 |

注意：这只是主要分工，不意味着其他成员不需要理解相关工作。三个人都应了解题目、核心模型、重要实验结果和最终结论。

## 三、各阶段具体分工

### 阶段一：赛题分析与选题

**目标：从 A、B 两道题中，选出最适合团队且最有竞争力的一道。**

这一阶段三个人完全独立分析，暂时不互相影响判断。

| 成员 | 具体任务 | 需要提交的成果 |
|---|---|---|
| A | 独立阅读两道题，拆解各题的子问题，分析可能采用的数学模型和解题路线 | 两题分析报告、个人推荐排序 |
| B | 独立分析两道题，重点考虑数据获取、算法实现、编程难度和时间成本 | 两题可行性分析报告、个人推荐排序 |
| C | 独立分析两道题，重点关注题目要求、潜在难点、结果验证方式和容易忽略的风险 | 两题风险分析报告、个人推荐排序 |

**集中讨论：**

1. 三个人交换各自的分析报告。
2. 比较三个人的推荐结果，找出一致和分歧。
3. 针对排名靠前的题目进一步讨论。
4. 重点检查全部子问题是否都有可行的解决路线。
5. 对前两名候选题进行小规模可行性验证。
6. 最终共同确定选题。

**本阶段交付成果：**
- `topic_decision.md`：选题分析与最终决定。
- `problem_decomposition.md`：最终选定题目的完整子问题拆解。

**阶段结束条件：** 三个人都理解为什么选择这道题，并且认可全部子问题的基本解决思路。

### 阶段二：独立建模与方案讨论

**目标：充分探索不同建模思路，最终形成统一的模型方案。**

选题确定后，三个人再次让各自的智能体独立思考，不急于直接编写代码。

| 成员 | 具体任务 | 需要提交的成果 |
|---|---|---|
| A | 重点研究核心问题，提出主要数学模型，完成变量、参数、假设和公式设计 | 核心模型方案、数学公式推导 |
| B | 独立研究其他可行模型，寻找替代方法或更简单的解决路线，分析不同方法的优缺点 | 候选模型及比较报告 |
| C | 独立审查 A、B 的方案，检查假设是否合理、公式是否成立、模型是否能够求解和验证 | 模型检查报告、潜在问题清单 |

**集中讨论：**

1. 三个人交换模型方案。
2. 比较不同方法的优缺点。
3. 对关键公式、参数和假设进行讨论。
4. 决定每个子问题采用什么模型。
5. 删除不必要的复杂模型，保留真正有价值的方法。
6. 确定各模型之间的联系，避免前后矛盾。

不要为了保留每个人的成果而强行组合模型。最终只保留最合理、最有必要的方案。

**本阶段交付成果：**

`MODEL_SPEC.md`，统一记录：
- 每个子问题的解决思路；
- 模型假设；
- 变量和符号；
- 核心公式；
- 参数来源；
- 求解方法；
- 模型之间的关系；
- 预期验证方式；
- 模型的局限。

**阶段结束条件：** 三个人共同认可模型方案，后续代码实现以这份文件为依据，不随意改变数学定义。

### 阶段三：代码实现与实验验证

**目标：将确定的数学模型转化为能够运行的程序，获得可靠的实验结果。**

这一阶段采用「一人主导代码，两人分别检查」的方式。

| 成员 | 具体任务 | 需要提交的成果 |
|---|---|---|
| A | 负责整体代码结构、核心算法实现、不同模块的整合，保证程序按照统一模型运行 | 可运行的核心代码、运行说明 |
| B | 协助算法实现，检查代码运行情况，测试不同参数和边界情况，进行必要的模型对比实验 | 测试记录、实验结果、对比表格 |
| C | 从数学角度独立检查代码实现是否符合公式，核对关键结果是否合理，开展必要的敏感性分析 | 数学检查记录、结果验证报告 |

**集中讨论：**

1. 检查代码是否正确实现模型。
2. 检查不同子问题的计算结果是否合理。
3. 比较不同模型或参数设置下的结果。
4. 分析模型在哪些情况下表现较好或较差。
5. 确定最终采用的参数和实验方案。
6. 对正式实验结果进行审核。

**数据与结果管理：**

这一阶段需要明确区分三类内容：

- 原始数据：保留最初获取的文件和来源，不随意修改。
- 处理后数据：记录清洗、筛选、转换等操作，确定统一版本。
- 正式实验结果：记录实际使用的代码版本、参数和运行结果。

如果发现模型或代码存在错误，允许修改和重新实验，但必须保留修改记录，不能直接覆盖旧结果。

**本阶段交付成果：**
- `DATA_MANIFEST.md`：数据来源和处理记录。
- `EXPERIMENT_PROTOCOL.md`：实验方法、参数和评价指标。
- `RESULTS_MANIFEST.md`：正式实验结果及对应代码版本。
- 完整可运行的代码和必要的运行说明。

**阶段结束条件：** 核心模型已经运行，重要结果经过检查，论文可以开始引用这些正式结果。

### 阶段四：论文结构与图表规划

**目标：确定论文需要展示哪些内容，以及每张图表应该放在哪里、说明什么。**

这一阶段由三个人共同讨论，不建议直接让绘图负责人自行决定所有图表。

| 成员 | 具体任务 |
|---|---|
| A | 根据模型和子问题，规划论文整体结构，确定每个章节需要说明的内容 |
| B | 根据实验结果，提出需要绘制的图表，判断采用什么形式展示最清晰 |
| C | 检查图表是否真正有助于解释模型和结果，检查是否存在重复或缺少关键证据的情况 |

**集中讨论：**

1. 确定论文整体章节结构。
2. 列出每个子问题需要展示的实验结果。
3. 讨论需要哪些图、表和流程图。
4. 确定每张图表的用途和放置位置。
5. 检查图表能否支撑对应的正文结论。

**本阶段交付成果：**

`FIGURE_PLAN.md`，建议包含：

| 图表名称 | 主要用途 | 计划放置位置 | 数据来源 | 负责人 |
|---|---|---|---|---|
| 模型总体流程图 | 展示整体建模思路 | 模型建立部分 | 模型结构 | B |
| 数据分布图 | 展示数据特征 | 数据分析部分 | 处理后数据 | B |
| 模型结果对比图 | 比较不同方法 | 结果分析部分 | 正式实验结果 | B |
| 敏感性分析图 | 展示参数变化的影响 | 模型检验部分 | 敏感性实验 | B |
| 其他必要图表 | 根据实际结果确定 | 对应章节 | 对应实验 | B |

以上只是示例，实际图表数量和内容由赛题决定。

**阶段结束条件：** 论文结构和图表清单确定，绘图人员明确每张图需要的数据和表达目的。

### 阶段五：论文撰写与图表制作

**目标：将已经完成的建模和实验工作整理成一篇完整、逻辑清晰的英文论文。**

这一阶段采用并行工作方式。

| 成员 | 具体任务 | 需要提交的成果 |
|---|---|---|
| A | 负责英文论文主体撰写，包括问题分析、模型假设、模型建立、公式推导和结果分析 | 完整论文初稿 |
| B | 负责全部正式图表的制作、调整、命名和图注撰写，确保图片与实验数据一致 | 正式图表文件、图表清单 |
| C | 阅读论文初稿，检查数学逻辑、公式、数据和结论是否一致，及时提出修改意见 | 分阶段审查意见 |

**写作要求：**

- 不要等所有实验结束后才开始写论文。
- 已经确定的题目分析、模型假设和公式可以提前撰写。
- 实验结果部分必须依据实际计算结果完成。
- 论文中的数字、图表和公式必须能够追溯到对应文件。
- 英文表达优先保证准确、自然和简洁，不追求复杂词汇。
- 不允许为了让论文看起来更有创新性而夸大实际工作。

**绘图要求：**

- 图表数据必须来自正式实验结果。
- 图表应清晰、统一，适合论文阅读。
- 每张图都应有明确的标题、编号和图注。
- 避免重复展示相同信息。
- 优先选择能够清楚说明问题的图表，而不是追求数量。

**阶段结束条件：** 论文初稿和正式图表均已完成，所有核心内容已经具备。

### 阶段六：论文优化、最终审查与提交

**目标：消除论文中的错误和不一致，形成最终提交版本。**

这一阶段由 C 主导终稿审查，A、B 配合修改。

| 成员 | 具体任务 | 需要提交的成果 |
|---|---|---|
| A | 根据审查意见修改数学内容、公式、论文结构和文字表达 | 修改后的论文 |
| B | 根据审查意见修改图表，检查图片质量、编号、图注和数据一致性 | 最终图表文件 |
| C | 负责整体审查、英文表达优化、章节衔接、引用检查和最终文件整合 | 审查报告、最终 PDF |

**重点检查以下内容：**

1. 是否完整回答了题目的全部要求？
2. 数学公式与代码实现是否一致？
3. 实验结果是否真实、可靠？
4. 图表和正文中的数字是否一致？
5. 每个重要结论是否有足够证据支持？
6. 英文表达是否自然、准确？
7. 公式编号、图表编号和参考文献是否正确？
8. 是否符合当届美赛官方提交规则？
9. AI 使用情况是否按官方要求披露？
10. PDF 是否能够正常打开，排版是否存在问题？

最后由三个人共同检查提交文件。

**本阶段交付成果：**
- 最终论文 PDF；
- 最终代码和必要的运行说明；
- 正式图表；
- 参考文献；
- 按当届规则需要准备的其他材料。

## 五、团队协作与文件管理约定

为了避免三个人的 Codex 会话相互独立、重要信息丢失，需要建立统一的项目文件管理方式。

建议所有人使用同一个 Git 项目仓库，重要成果通过文件交换，而不是仅在聊天群中传递。

核心共享文件：

| 文件 | 主要内容 |
|---|---|
| `topic_decision.md` | 最终选题依据 |
| `problem_decomposition.md` | 子问题拆解 |
| `MODEL_SPEC.md` | 最终统一模型 |
| `DATA_MANIFEST.md` | 数据来源和处理记录 |
| `EXPERIMENT_PROTOCOL.md` | 实验方案 |
| `RESULTS_MANIFEST.md` | 正式实验结果 |
| `FIGURE_PLAN.md` | 图表规划 |
| `DECISION_LOG.md` | 重要讨论和决定 |
| `REVIEW_REPORT.md` | 审查意见和修改记录 |

协作要求：

1. 每个阶段的负责人将最终成果整理成文件，供其他成员查阅。
2. 重要决定必须记录，避免不同智能体依据不同版本的信息工作。
3. 同一份核心文件尽量由一人负责修改，其他人通过意见和审查参与。
4. 修改已经确定的模型、数据和实验方案时，及时通知其他成员。
5. 使用 Git 保存重要版本，避免多人同时修改导致文件冲突。
6. 不必记录每一次普通对话，只记录真正影响最终结果的决定。

## 六、几个重要的团队约定

**约定一：独立思考，但不重复劳动。**

前期独立分析是为了获得不同思路，方案确定后应明确分工，不要三个人长期重复完成同一项任务。

**约定二：一个人主导，不代表一个人承担全部责任。**

例如 A 负责编码，但 B 和 C 仍然需要检查代码和结果。

**约定三：数据和结果可以修改，但必须有记录。**

发现错误时及时修正，不允许为了维持原有结果而忽视问题。

**约定四：论文和实验同步推进。**

已经确定的内容可以提前写作，避免最后阶段集中完成全部论文。

**约定五：最终决定由三个人共同确认。**

智能体的评分、建议和审查意见仅作为参考，不能代替团队判断。

**约定六：优先完成核心任务。**

不为了追求模型复杂、图表数量或流程完整而增加没有实际价值的工作。所有额外实验和分析都应当服务于题目解决、结果可信度或论文表达。

## 七、最终协作模式

我们的完整协作模式可以概括为：

**前期：三人独立思考，充分交换意见。**

**中期：确定统一方案，一人主导执行，两人协助验证。**

**后期：一人负责论文，一人负责绘图，另一人独立审查。**

**最后：三人共同确认终稿和提交材料。**

希望通过这种方式，让三个人的数学分析能力、编程能力和论文组织能力充分互补，同时利用各自的 Codex 智能体提高效率。

最终目标不是让 AI 完成尽可能多的工作，而是让团队在有限比赛时间内，得到一套真正合理、可靠、完整且能够自圆其说的数学建模解决方案。
